# Delivery and QA reference

Put the actual requested outcome first. Follow the user's language, format and
counts. A strategy request gets a usable strategy; a copy request gets complete
copy; a research request gets supported findings, not a plan masquerading as work.
Deliver supported partial work when blocked; name the exact missing input.

Then include:
- Workstreams and methods selected, why they fit, and where applied in this output.
- Verified sources/versions: immutable commit and method/license URLs when checked;
  bundled historical provenance when offline; never invented "latest" sources.
- U/V/A/X evidence distinctions, assumptions, limitations and blocked capabilities.
- QA: requested counts, factual claims, rights, sensitive data, source support,
  complete drafts, channel fit, single clear CTA where useful and version conflicts.
- DRAFT — unpublished / unscheduled status unless there is actual separately
  authorized external action evidence. List manual approval and next owner/action.
- One post-delivery feedback question, not mandatory setup before useful work.

For manual versioning include project alias, deliverable ID, version, status,
visible input IDs/versions, source IDs, date, changed sections and downstream
re-review dependencies. If no index is visible, say "visible latest; global latest
unconfirmed" and create only a provisional DRAFT. Never silently overwrite an
approved revision or infer approval from silence. Publish approval does not
approve reuse as a business rule. Ask for concise decision summaries, not hidden
chain-of-thought or private internal deliberation.

Static tests prove file contracts and archive integrity only. Native upload,
model adherence, real collaboration, cross-conversation reuse and business outcomes
are PENDING until directly observed and recorded.
